🔁 OTP State Machine

Every OTP row moves through these states. Terminal states (VERIFIED, EXPIRED, FAILED, BLOCKED) can't transition further.

stateDiagram-v2 [*] --> PENDING: create_otp PENDING --> SENT: adapter ACCEPTED PENDING --> FAILED: adapter REJECTED PENDING --> BLOCKED: anti-abuse (M2) SENT --> DELIVERED: DLR confirms (M2) SENT --> VERIFIED: correct code in time DELIVERED --> VERIFIED: correct code in time SENT --> EXPIRED: TTL or attempts VERIFIED --> [*] EXPIRED --> [*] FAILED --> [*] BLOCKED --> [*]

Two states are stubs today: delivered and blocked are defined in the enum but nothing sets them yet — they light up in Month 2 (DLR polling + anti-abuse). Defining them now means no migration churn later.
Audit-friendly design: we never delete OTP rows. attempt_count, used_at, and status transitions stay on the row so the Month-2 abuse engine can mine patterns (e.g. "5 OTPs to one number in 10s").
