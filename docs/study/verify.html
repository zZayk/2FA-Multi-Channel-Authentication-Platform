✅ Verify Flow

POST /otp/verify — the invariants that make a code one-time and time-bound. All enforced in otp_service.verify_otp.

flowchart TD Start(["POST /otp/verify"]) --> Auth{"valid API key?"} Auth -- no --> R401["401"] Auth -- yes --> Find["load latest ACTIVE otp for recipient"] Find --> Exists{"exists?"} Exists -- no --> Fail0["verified = false, status = expired"] Exists -- yes --> TTL{"past expires_at?"} TTL -- yes --> Exp1["set EXPIRED, verified = false"] TTL -- no --> Used{"already used?"} Used -- yes --> Fail2["verified = false"] Used -- no --> Cap{"attempts >= max?"} Cap -- yes --> Exp2["set EXPIRED, remaining = 0"] Cap -- no --> Match{"HMAC match?"} Match -- yes --> Win["set VERIFIED, stamp used_at, verified = true"] Match -- no --> Inc["attempt_count + 1"] Inc --> Lock{"now at max?"} Lock -- yes --> Exp3["set EXPIRED"] Lock -- no --> Retry["verified = false, remaining > 0"]
⏱️ TTL

Default 300s. After that the code is dead even if correct. Setting: OTP_TTL_SECONDS.

1️⃣ Single-use

used_at stamped on success. A verified code can't be replayed.

🔒 Max attempts

Default 5 wrong tries → locked (EXPIRED). Stops brute-forcing 6 digits.

Why "latest active" only? If a user requests 3 codes, only the newest valid one should verify. Older non-terminal rows are ignored — see _latest_active_otp.

Concrete demo

CORRECT CODE → 200

POST /otp/verify
X-API-Key: l2t_3vK9...redacted

{ "recipient": "+21620000000", "code": "418207" }

--- response ---
{ "verified": true, "attempts_remaining": 5, "status": "verified" }

WRONG CODE → 200 (note: still HTTP 200, body says false)

{ "recipient": "+21620000000", "code": "000000" }

--- response ---
{ "verified": false, "attempts_remaining": 4, "status": "sent" }

AFTER 5 WRONG TRIES → locked

{ "verified": false, "attempts_remaining": 0, "status": "expired" }
Design choice: verify returns HTTP 200 with verified: false for a wrong code — not a 4xx. The request was well-formed and authorised; the answer is just "no". Reserve 4xx for malformed/unauthorised requests.
