💡 Core Concepts

The named patterns behind the code. Open each for the "why" — then search the bold terms to go deeper.

Async I/O & the event loop FastAPI · asyncpg
Normal code does one thing at a time and waits on slow stuff (DB, network). Async code hands control back to an "event loop" during the wait, so one thread serves thousands of requests. That's why we use async def, async SQLAlchemy, and asyncpg everywhere.
DEEP: a blocking DB call freezes the whole loop → every user waits. One slow synchronous query can tank the entire API. Search: Python asyncio event loop, FastAPI concurrency.
HMAC vs bcrypt for secrets otp_service · api_key_service
bcrypt is deliberately slow to defend weak, human-chosen passwords against offline cracking. Our codes are random 6-digit / 32-byte secrets with short life + lockout — slowness buys nothing. HMAC-SHA256 keyed with SECRET_KEY is fast, and a DB dump alone can't be replayed (the attacker also needs the key).
DEEP: HMAC is deterministic — same input → same hash — which lets us look a key up by an indexed equality query. bcrypt's per-hash salt forbids that. Search: HMAC, keyed hash, constant-time compare.
Strategy / Adapter pattern services/channels
All channels implement one interface: ChannelAdapter.send(...). Dispatch calls get_adapter(channel).send(...) and doesn't care if it's SMS or Email. Add WhatsApp later = drop a new file, register it, done. Nothing upstream changes.
DEEP: each adapter is also an "anti-corruption layer" — it translates a messy external API (TunisiaSMS quirks, SMTP codes) into our clean SendResult. Search: Strategy pattern, Hexagonal architecture, anti-corruption layer.
Task queue & why Beat is separate Celery · Redis
The API drops a message on Redis (.delay()) and returns instantly. A worker pulls and runs it. Beat is a scheduler that fires periodic jobs. Beat must be a single container — run it inside scaled workers and you'd get N schedulers firing every job N times (duplicate SMS!).
DEEP: acks_late=True means a job is acknowledged only after it finishes, so a crashed worker's job is redelivered. Search: Celery periodic tasks, at-least-once delivery, idempotency.
Transient vs permanent errors → retries tasks/dispatch
A timeout or 5xx is transient — try again. A bad phone number or 401 is permanent — retrying just spams. We model this as two exception types; Celery's autoretry_for=(TransientChannelError,) retries only the right ones, with exponential backoff + jitter.
DEEP: jitter randomises backoff so a fleet of workers doesn't all retry at the same instant (thundering herd). Search: exponential backoff jitter, retry storm.
Dependency Injection & overrides Depends · tests
FastAPI Depends(get_session) / Depends(require_api_key) injects what a route needs. In tests we swap the real dependency for a stub via app.dependency_overrides — that's how schema tests run without a real DB or key.
DEEP: security deps resolve before body validation, so a missing key returns 401 before a malformed body could 422. Search: FastAPI dependency injection, test doubles.
Migrations & drift Alembic
Models describe the schema in Python; migrations are the versioned SQL that builds it in prod. They must agree. The drift test applies all migrations to a throwaway DB and diffs against the models — fails if someone edits a model but forgets a migration.
DEEP: create_all works once but can't evolve a live DB safely; migrations are reversible, ordered steps. Search: Alembic autogenerate, schema migration.
12-factor config & SecretStr core/config
All settings come from environment / .env via Pydantic BaseSettings — typed, validated, fail-fast on boot. Secrets use SecretStr so an accidental log prints **********, not the value.
DEEP: get_settings() is @lru_cached → one parsed config per process. Search: 12-factor config, pydantic-settings.
Each pattern's specific trade-off for this project is logged in docs/decisions.md with the reasoning.
